# Coding-Agent Prompt: Implement UMT-3.2 as a Single Rust Crate

You are implementing the core library for **UMT-3.2 (Unified Music Theory, Third Design, revision 3.2)** in Rust.

You are given this prompt together with the full `UMT-3.2.md` specification. Read the specification **completely before designing public APIs or writing implementation code**.

The target is a single Rust crate named:

```text
umt
```

All core functionality belongs in that one crate, organized by Rust modules rather than split into multiple crates.

This is intended to become a serious foundation for:

- algorithmic composition;
- music generation;
- adaptive tuning and temperament systems;
- score transformation;
- exact rhythmic construction;
- performance realization;
- live/realtime performance systems;
- notation/interchange adapters built on top of the core;
- conformance testing against UMT-3.2.

The implementation must preserve the mathematical and type distinctions in UMT-3.2. Do not collapse them merely to make the code shorter.

---

# 1. Authority and interpretation rules

Use this priority order when making decisions:

1. **UMT-3.2 normative requirements** (`MUST`, `MUST NOT`, `SHOULD`, `SHOULD NOT`, `MAY`) are authoritative.
2. This implementation prompt defines the intended Rust architecture where UMT-3.2 deliberately leaves implementation choices open.
3. If this prompt appears to contradict UMT-3.2, follow UMT-3.2 and record the conflict.
4. If UMT-3.2 is ambiguous, choose the least destructive representation: preserve information, preserve exactness, keep semantic types distinct, and avoid inventing equivalences.
5. If you discover a probable error in UMT-3.2, do **not** silently code around it. Document it in `docs/spec-issues.md`, include a minimal reproducer or proof/counterexample, and implement the most conservative behavior that does not corrupt data.

Treat Appendix A of UMT-3.2 as informative pseudotypes, not as an exact Rust API mandate. The normative mathematical sections and conformance laws take precedence.

Do not reinterpret the theory as "everything is a vector", "everything is a float", or "pitch and time are the same type". UMT-3.2 explicitly rejects those collapses.

# 4. Required architectural principle: semantic types stay distinct

UMT-3.2 distinguishes at least these four classes of operation:

1. exact structural maps;
2. representative-selection policies;
3. metric realization maps;
4. device quantizers.

Encode those distinctions in Rust.

A `TemperamentMap` must not be interchangeable with a tuning function.

A `RepresentativePolicy` must not be interchangeable with a homomorphic splitting.

A `TempoMap` must not be interchangeable with an interval tuning.

A device quantizer must not be passed where an exact quotient map is required.

Use newtypes, traits, enums, module privacy, and constructors to make invalid substitutions difficult or impossible.

Do not expose a generic public API like:

```rust
fn transform(x: Vec<f64>, matrix: Vec<Vec<f64>>) -> Vec<f64>
```

as the semantic foundation of the library.

---

# 5. Exact arithmetic policy

## 5.1 L0-L2 exact arithmetic

All exact structural arithmetic must be immune to integer overflow and floating-point identity errors.

Use arbitrary-precision integer and rational arithmetic for the semantic core.

A reasonable implementation is based on:

```text
BigInt
Ratio<BigInt> / BigRational
```

from mature Rust numeric crates.

Hide dependency-specific details behind crate-level aliases or newtypes where doing so improves API stability.

Suggested semantic names:

```rust
pub type Z = ...; // arbitrary-precision integer
pub type Q = ...; // exact rational
```

Do not use `i32`, `i64`, `f32`, or `f64` as the canonical storage for exact monzos, exact matrices, exact rational durations, kernel coordinates, or exact conformance checks.

## 5.2 Bounded/realtime representations

Bounded integer or floating representations may be introduced in compiled performance structures, but only after explicit validation.

For example:

```text
exact score / theory object
    -> validate against device/runtime limits
    -> compile
    -> bounded PerformancePlan
```

Never silently truncate a `BigInt` or `BigRational` to a bounded value.

# 6. Dynamic rank is the default

The core library must support arbitrary finite ranks loaded at runtime.

Do not make the primary public types depend on const-generic rank such as:

```rust
Monzo<const N: usize>
```

Const-generic helper types may be added later for specialized use, but the canonical public model must support arbitrary imported bases and temperaments.

A monzo therefore contains or references:

- basis identity;
- a dynamically sized integer exponent vector.

Likewise, temperament matrices and lattice bases are dynamically sized.

---

# 7. Basis identity is semantic

Two exponent vectors of the same length are not necessarily compatible.

For example, the vector:

```text
[1, 0, 0]
```

under basis `(2,3,5)` is not the same semantic object as `[1,0,0]` under `(2,3,7)`.

The Rust model must make basis mismatches detectable.

Do not implement unguarded:

```rust
impl Add for Monzo
```

if it can add monzos from unrelated bases.

Use one of the following patterns:

- checked addition returning `Result`;
- a context-bound typed handle system;
- an internal invariant proving compatible basis identity before arithmetic.

The public API must never silently add monzos from different bases.

# 8. TheoryContext and immutable registries

Use an immutable/frozen context model for shared semantic definitions.

A recommended shape is:

```rust
pub struct TheoryContext {
    // immutable registries after construction
}
```

constructed through:

```rust
pub struct TheoryContextBuilder {
    // mutable registration
}
```

The context may contain:

- bases;
- ambient lattices;
- temperament mappings;
- image and kernel lattice metadata;
- unit definitions;
- named representative policies;
- tuning definitions;
- notation-system identifiers if core notation hooks are present.

Use lightweight typed IDs/handles inside score/event objects rather than duplicating full definitions into every event.

Examples:

```rust
pub struct BasisId(...);
pub struct TemperamentId(...);
pub struct TuningId(...);
pub struct PolicyId(...);
```

Do not rely on process-local numeric IDs for persistent interchange. Native serialization must use explicit stable object identifiers or an equivalent reference scheme.

Distinguish:

- in-memory handles;
- stable serialized IDs;
- structural fingerprints/canonical hashes, if implemented.

# 10. Canonical integer-lattice representation

This is a high-priority implementation decision.

The core must support:

- free integer lattices;
- sublattices;
- kernels;
- images;
- membership tests;
- coordinate conversion;
- normal forms;
- exact rank;
- quotient-related data needed by UMT-3.2.

Use canonical or deterministic normal forms wherever practical.

Implement or depend on correct algorithms for Smith Normal Form and, where useful, Hermite Normal Form.

Do not ship an ad hoc normal-form implementation without strong tests.

The normal-form layer must be independently testable against mathematical invariants.

At minimum test:

- unimodularity of transformation matrices when supplied;
- reconstruction of the original matrix;
- divisibility ordering of Smith diagonal invariants;
- rank;
- image membership;
- kernel correctness;
- behavior on zero matrices;
- rectangular matrices;
- negative entries;
- non-surjective maps;
- large integer entries.

# 11. Represent the ambient lattice and reachable image separately

UMT-3.2 makes the distinction:

```text
V : Lambda_B -> Gamma
H = im(V) <= Gamma
```

fundamental.

The Rust API must preserve it.

Do not represent a temperament merely as a quotient rank.

Recommended concepts:

```rust
pub struct AmbientLattice { ... }
pub struct ImageLattice { ... }
pub struct AmbientElem { ... }
pub struct ImageElem { ... }
```

`ImageElem` should use intrinsic coordinates relative to a chosen/canonical basis for `H`.

Provide exact conversion APIs such as:

```rust
impl ImageLattice {
    pub fn embed(&self, x: &ImageElem) -> AmbientElem;

    pub fn from_ambient(
        &self,
        x: &AmbientElem
    ) -> Result<ImageElem, NotInImage>;
}
```

The 6-EDO case `[6,10,14]` must naturally expose:

```text
Gamma = Z
H = 2Z
```

rather than collapsing them.

An odd ambient EDO step must fail ordinary detempering under that map unless an explicit extension policy is provided.

# 12. TemperamentMap construction and validation

Use raw-versus-validated types.

For example:

```rust
pub struct RawTemperamentMap {
    ...
}

pub struct TemperamentMap {
    ...
}
```

with construction through a validating API:

```rust
impl TemperamentMap {
    pub fn new(...) -> Result<Self, TemperamentError>;
}
```

The validated form should make available, directly or lazily:

- domain basis/rank;
- ambient rank;
- exact matrix;
- rank;
- image lattice;
- kernel lattice;
- Smith/Hermite metadata as needed;
- surjectivity to the ambient lattice;
- image primitivity metadata where meaningful.

A map-derived kernel into a free abelian ambient lattice is automatically saturated; do not redundantly reject such kernels for saturation.

Directly supplied comma subgroups are different: if used to define a torsion-free regular temperament quotient, validate saturation as UMT-3.2 requires.

# 13. EDO and patent-val support

Provide a small but exact API for patent-val construction.

The formula must use the L3 valuation of formal basis generators as specified by UMT-3.2, not apply logarithms to formal symbols.

The rounding convention is part of the result/provenance.

Do not assume patent vals are surjective onto the ambient EDO step lattice.

Mandatory tests include:

- ordinary 12-EDO examples;
- 6-EDO `[6,10,14]`;
- zero map edge cases;
- basis-generator octave entry fixed to `N` where applicable.

# 14. Homomorphic splittings and representative policies are different APIs

Expose a strong interface for linear/homomorphic splitting:

```rust
pub trait HomomorphicSplit {
    fn split(&self, x: &ImageElem) -> Monzo;
}
```

and a separate more general interface for representative policies:

```rust
pub trait RepresentativePolicy<C> {
    type Error;

    fn choose(
        &self,
        class: &ImageElem,
        context: &C,
    ) -> Result<LiftDecision, Self::Error>;
}
```

A `LiftDecision` should include at least:

```rust
pub struct LiftDecision {
    pub lift: Monzo,
    pub residue: KernelElem,
    pub provenance: Option<ProvenanceId>,
}
```

A homomorphic split may implement or adapt into a representative policy.

The reverse conversion is not generally valid.

Do not assume a minimum-cost or adaptive representative policy preserves addition.

Implement the UMT lens laws for arbitrary right inverses and test them independently of linearity.

# 15. Residue is exact structure, not floating error

The temperament residue:

```text
rho_sigma(m) = m - sigma(V(m))
```

is an exact kernel element.

Model it as such.

Do not store it as cents, `f64`, or a generic error code.

Similarly, do not merge structural residue with:

- tuning deviation;
- empirical fit residual;
- temporal realization deviation;
- grid residual;
- device-control residual;
- orthographic residual.

Use distinct variants/types.

# 16. Complexity functions

Implement the UMT-3.2 profile distinction:

- `group_length`;
- `lattice_seminorm`;
- `lattice_norm`;
- `cost`.

Do not expose an ambiguous unqualified `Norm` abstraction that erases whether integer homogeneity is required.

The weighted L1 lattice norm and Tenney height on prime coordinates should be available.

For Tenney height:

- preserve exact prime exponent data structurally;
- the logarithmic numeric result is L3/real-valued;
- test the `log2(n*d)` identity for reduced rational `n/d` within an explicit numerical tolerance.

Do not identify complexity with psychoacoustic dissonance.

# 17. Torsors must be real types

UMT-3.2 intentionally separates points from intervals.

Reflect this in the Rust API.

Required conceptual operations:

```text
Point + Interval -> Point
Point - Point    -> Interval
Interval + Interval -> Interval
```

Do not define:

```text
Point + Point
```

as a core operation.

Use this distinction for at least:

- structural pitch points;
- realized/log-frequency pitch points;
- structural beat-time points;
- clock-time points.

A generic internal torsor helper is acceptable, but public domain types should remain readable.

# 18. Physical and metric units

Do not represent every L3 quantity as untyped `f64`.

Create newtypes for semantic quantities such as:

```rust
pub struct FrequencyHz(f64);
pub struct LogFrequency(f64);
pub struct Cents(f64);
pub struct Octaves(f64);

pub struct BeatTime(...);
pub struct BeatDuration(...);

pub struct ClockTime(...);
pub struct Seconds(...);

pub struct BeatsPerSecond(f64);
pub struct SecondsPerBeat(f64);
```

Choose exact internal names consistently.

Validate invariants such as positivity where required.

Use fallible constructors for values that cannot be NaN, infinite, zero, or negative under the semantic contract.

Strongly consider a finite-real wrapper or explicit validation strategy.

The library must prevent accidental use of seconds-per-beat as beats-per-second.

# 19. Regular tuning versus pitch-point realization

A regular tuning is an interval homomorphism.

Do not treat it by itself as an absolute-pitch function.

Provide explicit reference data:

- structural pitch reference point;
- realized pitch reference point;
- interval tuning.

Then expose the induced affine/equivariant pitch-point realization.

A concert-pitch change should modify reference data rather than mutate the interval lattice.

# 20. Non-regular realization

Represent contextual/non-regular realization as depending on a context object.

Do not encode:

```rust
fn realize(point: PitchPoint) -> LogFrequency
```

if the implementation actually depends on register policy, harmonic context, instrument state, measured inharmonicity, or time.

Use an API in the spirit of:

```rust
pub trait PitchRealizer<C> {
    type Error;

    fn realize(
        &self,
        point: &PitchPoint,
        context: &C,
    ) -> Result<RealizedPitchPoint, Self::Error>;
}
```

Context must be explicit in the type or call.

# 21. Chords and voice identity

A registered chord must preserve voice identity and multiplicity.

Do not model chords only as mathematical sets of pitch classes.

A suitable basic model is conceptually:

```rust
pub struct Chord {
    voices: ... // VoiceId -> PitchPoint
}
```

Unisons and doublings must survive.

Provide views that intentionally forget labels or register, but make those views explicit and potentially lossy.

# 22. Voice leading

Implement the structural span/relation model first.

A voice-leading relation supports:

- one-to-one continuation;
- split;
- merge;
- repeated relation;
- entry;
- exit.

Do not assume every voice leading is a permutation.

Keep these separate:

1. a declared transformation relation/span;
2. the cost of that declared relation;
3. an optimizer that searches over admissible relations;
4. a chord metric, if the metric laws are actually satisfied.

Balanced Wasserstein transport may only be called classical `W_p` when its preconditions hold, including equal total mass.

Unequal voice counts require an explicit strategy such as unbalanced transport, partial transport, or an edit/assignment model with birth/death penalties.

Do not normalize away multiplicity by default.

# 23. Structural time is exact

Use an exact rational duration type for the default structural beat-time profile.

Do not use floating point as the source of truth for ordinary written durations or tuplets.

Fixed structural event placement should retain exact rational onset and duration.

Unmeasured/constraint-based events should retain variables and constraints rather than a fabricated rational onset.

# 24. Event identity and scope

Define stable typed IDs:

```rust
pub struct EventId(...);
pub struct VoiceId(...);
pub struct StaffId(...);
pub struct PartId(...);
```

Event IDs should be stable within a score/document lineage.

Do not infer musical ancestry solely from ID equality.

Transformations that split, merge, insert, or delete events must carry explicit source-target relations.

Use event scopes equivalent to:

```rust
pub enum EventScope {
    VoiceLocal(VoiceId),
    StaffLocal(StaffId),
    PartLocal(PartId),
    Global,
}
```

Avoid a representation in which every event has `Option<VoiceId>` and invalid combinations are easy to construct.

A voice-local event must necessarily contain a voice identity in its representation.

# 25. TemporalPlacement should encode legal states

Use an enum rather than many optional fields.

Conceptually:

```rust
pub enum TemporalPlacement {
    FixedSpan {
        onset: BeatTime,
        duration: BeatDuration,
    },
    ConstraintPlacement {
        onset: TimeVarId,
        offset: Option<TimeVarId>,
    },
    Grace {
        anchor: EventId,
        rule: GraceRule,
    },
}
```

Refine names as appropriate.

Do not allow a fixed event to simultaneously carry contradictory unsolved placement variables unless a specifically documented hybrid type exists.

# 26. Ties and rests

A tie is a relation between distinct notated notehead events.

Do not merge tied noteheads in the score/L0 representation.

A realization may combine them into one sounding gesture while keeping the source relation.

A rest is a notation/voice-local event, not the global complement of sounding audio.

Do not derive rest events from "no sound" globally.

---

# 27. Rhythm trees

Implement ordered, hierarchical, exact rhythm trees.

Child weights must be positive exact values.

Flattening must preserve:

- order;
- exact parent total;
- exact rational boundaries when the source is exact.

Flattening is lossy, so retain the tree as the source structure.

Do not reconstruct nested tuplets by guessing from flattened onset times.

---

# 28. Meter and grouping

Keep meter and grouping as different structures.

Do not reduce both to a single array of beat strengths.

The API should be able to represent:

- 6/8 versus 3/4 with the same total span;
- additive grouping such as 2+2+3;
- hypermeter;
- anacrusis;
- cyclic pulse patterns.

Do not require all metric levels to be subgroups.

---

# 29. Tempo ratios versus time-grid quantization

Keep exact multiplicative tempo-proportion operations separate from additive grid quantization.

A tempo-proportion temperament, when intentionally used, belongs to the exact proportion machinery.

PPQN rounding belongs to device/time quantization.

Do not share one generic "temper" function between them.

---

# 30. Tempo maps

A homeomorphism-profile tempo map must satisfy the UMT-3.2 requirements.

Expose the distinction between:

```text
seconds per beat
```

and:

```text
beats per second
```

The derivative of clock time with respect to beat time has the former dimension; its reciprocal has the latter where defined.

A zero-structural-duration physical pause cannot be silently represented as an ordinary strictly increasing homeomorphism. Use the explicit UMT mechanisms for pauses/constraints/augmented structural spans.

---

# 31. Temporal constraint networks

Do not create one universal solver that pretends all constraints are STP edges.

Represent solver/profile distinctions structurally.

At minimum:

```rust
pub struct StpProblem { ... }
pub struct LinearTemporalProblem { ... }
pub struct HybridTemporalProblem { ... }
```

or an equivalently safe API.

STP constraints are difference bounds.

Ratio constraints that cross-multiply to general linear inequalities are not ordinary difference edges.

External predicates are named typed references/contracts, not arbitrary executable code serialized into a score.

Do not invent a positive lower bound `delta` when the source semantics only specify a strict positive denominator.

If a selected solver cannot express a strict inequality exactly, report that limitation or use a justified solver-specific representation.

---

# 32. Temporal solver results

A temporal solver result must distinguish at least:

- exact solved;
- approximate solved;
- partial/residual external conditions;
- inconsistent/infeasible;
- unsupported by this solver profile.

Do not return only a map of `TimeVarId -> f64`.

Preserve provenance, exactness status, and unresolved predicates.

# 33. Optimization outcome is a first-class type

UMT-3.2 explicitly allows:

- infeasibility;
- non-unique minimizers;
- unattained infima;
- approximate solutions.

Represent these states.

A recommended design is:

```rust
pub enum OptimizationOutcome<T, C> {
    Exact {
        solution: T,
        cost: C,
    },

    Multiple {
        selected: T,
        cost: C,
        // metadata describing non-uniqueness as appropriate
    },

    Approximate {
        solution: T,
        cost: C,
        guarantee: ApproximationGuarantee<C>,
    },

    Infeasible,

    InfimumNotAttained {
        infimum: C,
    },
}
```

Adapt as needed.

Do not represent all outcomes as `Result<T, Error>`, because non-uniqueness and approximation are not ordinary failures.

# 34. Quantization APIs return evidence

Do not define a semantic quantizer as:

```rust
fn quantize(x: Q) -> i64;
```

Return the represented value and residual/evidence.

For example:

```rust
pub struct Quantized<T, R> {
    pub value: T,
    pub residual: R,
}
```

For hierarchical rhythm quantization, return a structure that retains:

- exact source tree/reference;
- integer allocations;
- local residuals;
- endpoint status;
- infeasibility/collision information.

Implement at least:

- floor;
- ceiling;
- nearest with explicit tie-breaking;
- endpoint-preserving allocation;
- hierarchical constrained allocation.

Do not claim the floor/ceiling order adjunction for nearest rounding.

# 36. Provenance

Avoid copying arbitrary JSON blobs into every semantic object.

- algorithm name;
- algorithm version;
- parameters;
- random seed when relevant;
- tolerance;
- source measurement IDs;
- import format and version;
- parent/source objects.

Provenance must be serializable.

# 37. Source structures are immutable by default

Do not mutate a score into its realization.

Keep these conceptual layers separate:

```text
Score
    -> Realization
    -> PerformancePlan
    -> RuntimeState
```

`Score` is the exact/structural authoring object.

`Realization` contains chosen tunings, solved time, trajectories, residuals, and provenance.

`PerformancePlan` is a bounded, device/runtime-oriented compiled representation.

`RuntimeState` is mutable live state and should not be required for pure theory operations.

This separation is especially important for re-realization at a different tuning, tempo policy, PPQN, sample rate, or output device.

---

# 38. Realtime boundary

The semantic core does not need to be realtime-safe.

It may use:

- arbitrary-precision arithmetic;
- allocation;
- normal-form algorithms;
- graph algorithms;
- optimization;
- serialization;
- locks during authoring if necessary.

However, the crate should support compiling a validated `PerformancePlan` for realtime systems.

Document realtime guarantees in `docs/realtime.md`.

The realtime plan should aim for:

- no arbitrary-precision arithmetic on the performance thread;
- bounded allocation or preferably no allocation on the realtime thread;
- no blocking filesystem/network access;
- no mutex contention in the timing/audio-critical path;
- resolved device mappings;
- validated bounded numeric ranges;
- precomputed tuning/control values where practical.

Do not claim `RealtimeSafe` unless the type and API actually satisfy a documented contract.

# 39. Native serialization

Implement a native UMT serialization model matching UMT-3.2 semantics.

Use `serde` behind a feature if appropriate.

The serialized model must be versioned.

Requirements:

- preserve arbitrary-size integers exactly;
- preserve rationals exactly as numerator/denominator or an equally exact canonical encoding;
- preserve matrix dimensions and entries;
- distinguish ambient lattice from image lattice;
- preserve basis identities/references;
- preserve representative-policy metadata;
- preserve chosen adaptive lifts when required for round trip;
- preserve event IDs and event relations;
- preserve rhythm-tree topology;
- preserve exact structural durations;
- preserve temporal constraints and external predicate references;
- preserve residual variants and units;
- preserve provenance;
- preserve entry-layer/profile information for objects that begin at L2 or L3;
- allow unknown future extension fields where feasible without silently treating them as understood.

Do not serialize `BigInt` or rational values through JSON floating point.

# 40. External format adapters

The first core release does not need full MusicXML, MEI, MIDI, Scala, or MNX implementations.

Design the internal model so adapters can be added later.

If any adapter is implemented during this work:

- place it behind an optional feature;
- pin the supported external format version/profile;
- emit explicit loss information;
- do not make the external format a core dependency.

Native serialization is higher priority than external adapters.

Prefer mature, focused dependencies.

Likely acceptable categories:

- arbitrary-precision integers/rationals;
- numeric traits;
- serde;
- error derivation;
- property testing;
- stable ID helpers if justified.

Avoid:

- large GUI/audio frameworks;
- a mandatory async runtime;

- license;

# 47. Property-based testing

Use property-based tests for algebraic laws.

At minimum test:

## Exact lattice arithmetic

- associativity;
- zero;
- inverse;
- dimension/basis mismatch rejection.

## Rational valuation

- `r(m+n) = r(m) * r(n)` for rational basis profiles.

## Temperament map

- homomorphism law;
- kernel iff mapping to zero;
- map-derived kernel saturation for nonzero integer multiples;
- image embedding/coordinate round trip.

## Representative policy

- right-inverse law;
- residue in kernel;
- GetPut;
- PutGet;
- PutPut;
- homomorphism only when the policy claims it.

## Torsors

- action associativity;
- identity;
- point difference/action round trip;
- interval cocycle relation.

## Complexity

- group-length laws;
- integer homogeneity for lattice seminorm/norm;
- identity of indiscernibles for lattice norm.

## Quantization

- grid identity;
- floor one-sided law;
- ceiling one-sided law;
- nearest residual bound;
- endpoint-preserving sum invariant.

## Rhythm trees

- positive child weights;
- exact partition of parent;
- flattening preserves total.

## Serialization

- exact arbitrary-size values survive round trip;
- no exact structure is reconstructed from rounded L3 values when source data were available.

# 50. Performance and caching

Correctness comes first, but avoid pathological repeated algebra.

Potential caches:

- Smith/Hermite form;
- kernel basis;
- image basis;
- image coordinate transformations;
- basis valuations;
- canonical fingerprints.

Cache only immutable derived values.

Use `OnceLock`, immutable memoization, or context-owned cache structures as appropriate.

Do not make semantic equality depend on cache state.

Benchmark:

- common 5-limit/7-limit monzo arithmetic;
- normal-form construction for moderate matrices;
- image membership;
- rhythm-tree flattening;
- quantization;
- large score traversal;
- performance-plan compilation.

Do not micro-optimize before the invariants are correct.

# 51. Thread-safety

The frozen semantic context and score structures should preferably be `Send + Sync` where practical.

Do not introduce `Rc<RefCell<_>>` throughout public core types if immutable `Arc`/arena/ID patterns can avoid it.

Mutable builder types need not be shareable.

Runtime performance state may be mutable and specialized.

Document thread-safety guarantees.

# 53. Determinism

The same exact input, policy, parameters, and random seed should produce the same structural result where the algorithm is specified as deterministic.

For algorithms with multiple mathematically valid outputs, either:

- define a deterministic tie-breaker; or
- report non-uniqueness and selected output provenance.

Canonicalization routines must not depend on address order or nondeterministic map iteration.

This is important for reproducible composition and serialized diffs.

# 54. Versioning

Define an internal native schema version independent from the Cargo package version.

For example:

```rust
pub struct UmtSchemaVersion {
    pub major: u16,
    pub minor: u16,
}
```

The initial schema should identify itself as implementing the UMT-3.2 semantic profile.

Do not assume future UMT revisions are backward-compatible.

Unknown future fields should not be silently interpreted as current semantics.

# 55. Do not overbuild notation in v1

UMT includes L0 notation hooks, ties, spelling, and orthographic residuals.

Implement enough structure to preserve:

- spelling identity;
- notation-system ID;
- ties;
- event relationships;
- orthographic residual payload;
- exact semantic interpretation links.

Do not attempt to build a complete engraving model, page-layout engine, or all historical notation systems in the first core release.

The core must be capable of carrying notation-preservation data without owning every notation policy.

---

# 56. Do not overbuild psychoacoustics in v1

Provide extension interfaces for empirical/spectrum-conditioned models if needed.

Do not make Sethares-style dissonance, critical-band models, or a universal consonance metric required dependencies of the first core implementation.

The core distinction to preserve is:

- exact arithmetic complexity;
- empirical or spectrum-conditioned real-valued models;
- optional inference between them with residual/provenance.

---

# 57. No hidden loss

Any operation that intentionally forgets information should say so in its type, result, or documentation.

Examples:

- registered pitch -> pitch class;
- voice-labeled chord -> unlabeled multiset;
- exact rhythm tree -> flattened times;
- L1 exact pitch -> L2 tempered class;
- L3 trajectory -> sampled device events;
- notation -> semantics without orthographic residual.

Prefer APIs like:

```rust
fn project_pitch_class(...) -> ProjectionResult<...>
```

or clearly named `forget_*` / `project_*` methods rather than innocuous conversions that appear lossless.

Do not implement lossful `From<T> for U` conversions when the loss is musically meaningful.

Use `TryFrom`, explicit projection methods, or results carrying loss metadata.

---

# 58. Avoid panics in semantic APIs

Public library operations should return typed errors for invalid input.

Reserve panics for:

- violated internal invariants indicating a library bug;
- impossible states after validated construction.

Indexing helpers may panic only when clearly documented as ordinary Rust indexing behavior; safe checked alternatives should exist for external/untrusted dimensions.

Use documentation tests where appropriate.

# 63. First concrete task

Do **not** begin by implementing MIDI, adaptive JI optimization, or a large `Score` type.

Begin with a design-and-test slice that proves the foundations:

1. create the crate and module skeleton;
2. choose exact integer/rational dependencies;
3. implement `Basis`, `BasisId`, `Monzo`, `IntMatrix`, `AmbientLattice`, `ImageLattice`, and `TemperamentMap`;
4. implement basis-checked monzo arithmetic;
5. compute image/kernel data exactly;
6. implement the `[2]: Z -> Z` counterexample;
7. implement the 6-EDO `[6,10,14]` example;
8. prove through tests that odd ambient 6-EDO steps are not automatically image elements;
9. implement a homomorphic split and a deliberately non-homomorphic representative policy;
10. verify the right-inverse, residue, and lens laws;
11. serialize these objects exactly;
12. only then proceed upward to pitch/time/score layers.

This foundation determines whether equality, hashing, serialization, detempering, and every later musical subsystem will be trustworthy.

# 65. Final principle

The most important implementation rule is:

> **Preserve exact symbolic proportion, structural quotient, metric realization, and device approximation as different semantic layers, and make every loss or policy choice explicit.**

The Rust type system should make the mathematically invalid or semantically lossy shortcut harder than the correct representation.

Build the foundation for generative and performance systems from that principle.
